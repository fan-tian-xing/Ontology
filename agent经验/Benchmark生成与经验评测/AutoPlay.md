# 通过环境探索自动生成任务：AutoPlay 论文调研及研究思路

## 1. 研究目标与论文定位

### 1.1 论文全名、发表信息与阅读版本

- **英文全名：** *Scaling Synthetic Task Generation for Agents via Exploration*。
- **方法名称：** AutoPlay。
- **中文释义：** 通过探索扩展智能体合成任务生成规模。
- **作者：** Ram Ramrakhya、Andrew Szot、Omar Attia 等。
- **正式发表：** ICLR 2026 会议论文，2026 年。

## 2. 论文动机：生成任务需要知道环境“现在能做什么”

训练交互式 Agent 既需要任务描述，也需要对应操作示范。人工收集成本高；只告诉模型应用名称或功能简介，模型又容易生成泛泛的请求，甚至引用不存在的数据、对象或功能。

作者认为，高质量任务必须同时具备覆盖度、可执行性和可验证性。环境的当前数据、可用功能与交互规则难以仅靠模型先验获得，因此先主动探索，再用实际观察到的内容约束出题。[依据：正文 §1]

## 3. 问题定义：任务不只是自然语言指令

一个任务由目标 g 和起始状态 s0 配对组成。执行轨迹由观察和动作序列构成；UI 场景中，观察主要是截图，动作包括点击、输入和滚动。

这一表示对自动构建 Benchmark 很重要：同一句“修改某会议时间”，如果起始环境里没有该会议，或数据状态不同，就不是同一道可复现的任务。AutoPlay 因而保留任务与环境初始状态之间的联系。[依据：正文 §3.1；后一句为本笔记解读]

## 4. 方法一：无特定目标的环境探索

### 4.1 Explorer 怎样收集环境上下文

Explorer 获得当前截图、已有探索记忆及探索提示，尝试访问新的界面、对象和功能。每轮收集截图与动作序列；环境重置后继续探索，并利用前几轮的摘要减少重复。

由于完整图像轨迹占用上下文较大，Summarizer 将每轮探索总结成文本记忆。阶段结束得到多条 environment context（环境上下文），供下一阶段出题。[依据：正文 §3.2、算法 1]

### 4.2 探索轨迹与成功解题轨迹的区别

Explorer 并不是先完成某个指定任务，再把那条轨迹改写成题目。它的轨迹提供“有哪些对象、哪些操作可行、当前有什么数据”的依据，可以支撑多个不同任务。

因此，探索轨迹本身不保证后来每一道题都有成功解法。生成后的任务还需要另行执行和验证。[依据：正文 §3.2；验证要求为方法逻辑解读]

## 5. 方法二：探索上下文与出题指南联合生成

### 5.1 为什么还需要任务指南

同一段探索可以诱导很多近似任务。AutoPlay 用 task guidelines 控制任务类别，包含功能使用、信息检索、功能组合和子任务重复等方向。生成器同时读取探索轨迹与一种指南，输出多个目标，并绑定轨迹对应的初始状态。

其中的组合指南用于扩展任务类型，不代表论文已验证这些任务必须借助多段历史经历才能解出。[依据：正文 §3.2、图 1；最后一句为评测范围分析]

### 5.2 执行和验证怎样衔接

Task Executor 的规划器读取指令、截图、动作历史和反思结果，提出高层动作；grounding 模型把点击等动作转为像素坐标，Reflection 工具比较前后观察，为后续步骤提供反馈。

论文用 GPT-4o 作为规划、反思及示范轨迹验证后端；移动端 grounding 使用 UI-TARS-1.5 7B，桌面端使用 GTA1-7B。验证器读取指令与图像—动作轨迹，先概括执行过程，再推理并判定成功或失败，不读取特权环境状态。

生成的约 **2 万 Android 任务**和 **1 万 Ubuntu 任务**，经执行及验证，分别得到约 **8 千**和 **3.5 千**条成功轨迹用于 SFT。因此，“生成任务数”不等于“已验证成功示范数”。[依据：正文 §3.3]

### 5.3 总体流程

~~~mermaid
flowchart LR
    A[应用与初始状态] --> B[多轮探索并总结记忆]
    B --> C[探索轨迹加任务指南]
    C --> D[生成多个任务]
    D --> E[Executor 实际执行]
    E --> F[MLLM 验证轨迹]
    F --> G[成功示范用于 SFT]
    D --> H[任务与验证反馈用于 RL]
~~~

RL 阶段使用 Qwen2.5-VL-32B-Instruct 作为轨迹验证器，以成功/失败提供二元奖励，用 GRPO 训练；实际为稳定性限制在执行器曾至少成功一次的约 8 千个移动端任务。不能把方法理论上可利用更广任务，写成实验实际使用了全部任务。[依据：正文 §3.4]

## 6. 实验怎么验证自动生成方法有效

### 6.1 两层证据：任务质量与下游训练价值

论文先比较不同任务生成方案能否产出可执行、多样的任务，再训练 Qwen2.5-VL 系列 Agent，在 AndroidWorld 和 OSWorld 测试。

训练轨迹筛选依赖 MLLM 判断；最终 Benchmark 评估使用可读取环境状态的标准成功验证器。两者不同，因此下游结果并非仅由训练时同一个模型自我评价。Pass@1 是五次独立试验的平均成功率，Pass@5 为五次中至少一次成功的任务比例。[依据：正文 §4.1]

### 6.2 下游主实验

以下来自可读取版本的表 1，提升按相同规模底座计算，单位为百分点：

| 平台与模型 | 底座 Pass@1 | AutoPlay Pass@1 | 提升 |
| --- | ---: | ---: | ---: |
| AndroidWorld / 7B | 19.5% | 40.1% | +20.6 |
| AndroidWorld / 72B | 35.0% | 47.9% | +12.9 |
| OSWorld / 7B | 3.7% | 11.4% | +7.7 |
| OSWorld / 72B | 4.4% | 14.5% | +10.1 |

3B 模型在 AndroidWorld 上经 RL 从 **34.2%** 升至 **39.9%**，增加 **5.7 个百分点**。这些数据支持生成任务和筛选轨迹具有训练价值；不能据此推断模型在测试时读历史笔记就一定能迁移。[依据：正文 §4.1、表 1]

摘要写的“移动端最高约 20.0%、桌面端 10.9%”与可读取表 1 的具体差值不完全一致。本笔记逐项采用表格对照，不将其拼成同一组结果。

### 6.3 消融：探索与指南究竟有什么贡献

作者在 AndroidWorld 中让各方案都生成 5,000 个任务，使用相同执行器和验证器，再训练 7B 模型：

| 生成方案 | 生成任务上的执行成功率 | 训练后 AndroidWorld Pass@1 |
| --- | ---: | ---: |
| 不探索，只给静态环境信息 | 21.3% | 28.8% |
| 串行提出并执行短子目标 | 56.4% | 21.6% |
| AutoPlay 去掉任务指南 | 43.5% | 26.7% |
| 完整 AutoPlay | 46.0% | 38.2% |

这组对照比单看主实验更能解释方法：完整探索优于静态信息，任务指南也改善下游训练效果。串行短子目标方案最容易被执行器完成，却训练出较弱模型，说明“生成题的通过率高”不能独立代表数据质量好。[依据：正文 §4.2、表 2]

消融控制了生成任务候选数，但不同执行成功率带来不同数量的成功轨迹，不能把它当作严格等成功轨迹数或等 token 的比较。这是解释实验时仍需保留的限制。

## 7. 对经验迁移 Benchmark 的借鉴与改造

以下为本课题建议，不是 AutoPlay 原论文的经验迁移实验。

### 7.1 可复用的构建模块

- **环境探索：** 自动发现可用对象、功能和真实约束，降低凭空出题。
- **一条探索支撑多个目标：** 提高生成效率，但保留各目标独立验证。
- **可重置初始状态：** 将任务固定为“目标＋环境状态”。
- **任务指南：** 细分对象变化、条件变化和组合变化，控制覆盖。
- **双层验证：** 大规模模型筛查之外，保留独立环境验证或人工抽检。
