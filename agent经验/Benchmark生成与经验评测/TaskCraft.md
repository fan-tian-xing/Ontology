# 可控难度与组合任务自动生成：TaskCraft 论文调研及研究思路

## 1. 研究目标与论文定位

本研究需要自动生成既能检验经验迁移，又能检验多段经验组合的新任务。TaskCraft 的价值在于提供明确的任务结构操作：从工具相关的原子任务开始，通过深度扩展增加依赖链，通过宽度扩展组合子问题。它主要研究任务与训练数据生成，并没有直接完成“历史经历→新任务”的受控经验迁移评测。

### 1.1 论文全名、发表信息与版本差异

- **英文全名：** *TaskCraft: Automated Generation of Agentic Tasks*。
- **中文释义：** TaskCraft：智能体任务的自动化生成。
- **作者：** Dingfeng Shi、Jingyi Cao、Qianben Chen 等。
- **正式发表：** ICLR 2026 会议论文，2026 年。

## 2. 论文动机：作者想自动生成什么样的题

TaskCraft 想批量生成这样的任务：**Agent 需要查网页、读 PDF 或看图，从外部材料取得信息，再给出答案。** 生成的题目还应能逐步变复杂，并保留答案依据和求解过程，供训练与评测使用。

难点在于，直接让 LLM“出一道需要查资料的题”，它可能生成“法国首都是哪里”这样凭已有知识就能答的问题；也可能编出资料里根本没有答案的题。这两类题都不能很好地检验工具使用能力。

所以作者的基本做法是：**先从真实材料里找到有依据的答案，反向生成一个简单问题；筛掉不合适的题，再把合格小题扩成复杂题。**

下面依次解释：小题是什么、怎样出题、为什么筛选，以及怎样扩展。所有带“青禾研究所”的例子均为帮助理解而虚构，机构、材料、数字和日期都不是论文实验数据。

## 3. 方法一：先生成需要外部信息的“原子任务”

### 3.1 原子任务到底是什么

这里的“原子任务”（atomic task）是**作者用来搭建复杂题的基本问题单元**：理想情况下，调用一次目标工具取得一份材料，再从中找出答案即可。

例如，假设有一份《青禾研究所 2024 年项目报告》，其中写着：

> 2024 年完成项目 73 项，2023 年完成项目 61 项。

可以生成一道原子任务：

> 请读取《青禾研究所 2024 年项目报告》，回答该研究所 2024 年完成了多少项项目。

解题路径是：定位报告 → 用 PDF 阅读工具取得内容 → 找到“2024 年完成项目数” → 回答“73 项”。

“原子”强调它是后续扩展的基本单元，不表示它完全不需要推理，也不是把一次点击或一次输入当成一道任务。论文概念上以一次目标工具调用为基础，实际验证会放宽到有限工具步数，例如三步。因此，不能把“原子任务”理解成严格保证只调用一次 API 的题。

### 3.2 出题器怎样把材料变成一道题

先分清两个角色：

- **出题器：** 已经读到来源材料，可以从中选答案并编题。
- **做题的 Agent：** 获得题目和资源线索，需要自己调用工具取得材料；不会因为出题器读过，就自动拿到那段答案证据。

以上面的虚构报告为例：

| 阶段 | 具体做什么 | 得到什么 |
| --- | --- | --- |
| 1. 准备来源 | 选取报告，取得文件路径或资源链接 | 能定位报告的入口 |
| 2. 调用工具 | PDF 工具读取报告 | 报告文字、表格等内容 |
| 3. 选答案 | 从内容中选一个可核查的事实 | “73 项”及对应证据 |
| 4. 确定提问关系 | 说明这个数字对应哪个对象、年份和指标 | “该研究所 2024 年完成项目数” |
| 5. 写成问题 | 把来源线索与提问关系写成自然语言 | 上一节的原子任务 |

因此，这里的“反向生成”是指：**出题时先有材料和答案，再写问题；解题时则从问题出发，重新找材料和答案。** 它降低了凭空编造题目和标准答案的风险，但仍需检查问题有没有写错。

论文中的符号可以对应为：

| 符号 | 通俗含义 | 本例 |
| --- | --- | --- |
| T | 用什么工具读材料 | PDF 阅读工具 |
| iT | 用来定位并调用工具的入口 | 报告名称、文件路径或链接 |
| C | 工具读出来的内容 | 报告正文与表格 |
| R | 从材料中要找的关系或信息 | 该机构在指定年份完成的项目数 |
| a | 标准答案 | 73 项 |
| q | 最后生成的问题 | “2024 年完成多少项项目？” |

**iT 是找材料的线索，C 才是材料内容；题目告诉你去读哪份报告，不等于已经把报告答案给了你。** [论文依据：arXiv v2 §2、§3.1](https://arxiv.org/html/2506.10055v2)

### 3.3 为什么要保留“工具 Agent 能答对，无工具模型答不对”的题

因为作者希望筛出的基本单元，能够体现**外部信息和工具交互的价值**。

例如：

- “法国首都是哪里？”——模型可能早已知道。即使 Agent 顺手查了网页才回答，也很难说明工具对答题有必要。
- “指定报告中 2024 年完成了多少项项目？”——答案依赖具体材料，更适合检查 Agent 是否会定位来源、读取并提取信息。

如果只要求“用了工具的 Agent 答对”，可能保留大量本来不用工具也能答的题，后面训练或评测时就难以区分模型是在调用工具，还是直接凭记忆回答。

如果只要求“无工具模型答错”，又可能留下错误题、歧义题，或者当前 Agent 也无法完成的题。因此作者同时检查两侧的回答，希望筛出“借助工具确实能取得正确答案，且比无工具回答更好”的候选。

### 3.4 两组模型分别得到什么，怎样判定

筛选时，把同一个候选问题交给：

1. **可用工具的 Agent：** 可以检索、阅读相关外部材料；
2. **无工具的推理 LLM：** 没有通过工具获得这些材料，依靠自身知识与推理回答。

判断模型再将两侧回答与生成时保留的标准答案比较。

下面用“答对/答错”简化解释筛选动机，不是完整的实现判定表：

| 有工具一侧 | 无工具一侧 | 为什么保留或排除 |
| --- | --- | --- |
| 答对 | 答错 | 最符合目标：工具侧能够解决，且体现了外部信息的增益 |
| 答对 | 答对 | 工具必要性的证据不足，不是这一筛选策略的重点 |
| 答错 | 答错 | 当前流程没有得到可用的成功解法，需要排查题目或求解过程 |
| 答错 | 答对 | 不符合“工具侧表现更好”的目标 |

正文用“只有工具侧得到标准答案”来解释筛选；附录 C.1 采用两侧得分比较等条件，其中 AgentScore 要高于 LLMScore。理解其动机时，可以抓住“工具侧相对无工具侧更有优势”，上面的答对/答错表用于解释这一思路，不是完整实现规则。[论文依据：arXiv v2 §3.3、附录 C.1](https://arxiv.org/html/2506.10055v2)

### 3.5 这个筛选能证明什么，不能证明什么

它提供的是**相对所用模型和预算的工具依赖证据**。某个无工具模型这次答错，不等于任何模型都不可能凭记忆答对；工具侧答错，也不等于题目一定无解。

同样，一道题即使被筛掉，也不代表它完全没有训练价值，只是它不符合作者在这个阶段优先寻找的样本特征。

筛选合格后得到的产物，可以理解为“一道基本题＋标准答案＋证据来源＋可记录的求解过程”。这些基本单元用于下一阶段的结构扩展。

## 4. 方法二：怎样把原子任务扩成复杂任务

### 4.1 深度扩展：先找出该读哪份材料，再回答原问题

继续使用前面的虚构例子。原题已经直接告诉 Agent 报告名称：

> 读取《青禾研究所 2024 年项目报告》，回答该所 2024 年完成项目数。

现在假设“晨星资料库”的年度报告目录中有这样一条记录：

| 发布机构 | 发布日期 | 报告及链接 |
| --- | --- | --- |
| 青禾研究所 | 2025 年 2 月 18 日 | 《青禾研究所 2024 年项目报告》及 PDF 链接 |

目录里没有“73 项”这个答案，只能帮助找到报告。先构造一个新增小问题：

> 晨星资料库的年度报告目录中，青禾研究所在 2025 年 2 月 18 日发布的报告是哪一份？

这个新增问题的答案是**原报告名称或链接**。再把它与原题合成：

> 请在晨星资料库的年度报告目录中，找到青禾研究所在 2025 年 2 月 18 日发布的报告，并回答其中记录的 2024 年完成项目数。

现在需要：

1. 浏览目录，识别报告并取得链接；
2. 读取报告，查出项目数。

**最终答案仍可保持“73 项”，但原本直接给出的报告入口，变成了需要先解决的问题。** 这就是增加一层依赖。这里用目录包含报告的关系，说明论文所要求的上层入口与原入口之间的关系；不是随意把报告名改得更长。

进一步扩展，还可以先找目录所属页面，再找报告。不过每增加一层都要检查它是否真的需要额外获取信息，不能只在文字上声称多了一跳。[论文依据：arXiv v2 §3.2、附录 B](https://arxiv.org/html/2506.10055v2)

### 4.2 宽度扩展：需要分别完成多个分支

再准备另一道虚构原子题：

> 读取青禾研究所的项目公告网页，回答 2024 年启动了多少项新项目。

假设该网页给出的答案是“41 项”。现在有两道基本题：

| 分支 | 需要读取的来源 | 要求取得的信息 |
| --- | --- | --- |
| A | 项目报告 PDF | 完成项目 73 项 |
| B | 项目公告网页 | 启动新项目 41 项 |

将它们合成：

> 请分别根据项目报告和项目公告，列出青禾研究所 2024 年完成项目数、启动新项目数，并注明来源。

Agent 需要分解问题，分别完成 A、B，再组织两个结果。这是宽度扩展的基本思路。论文写的“问题相加、答案相加”表示合并问题与结果，不要求把两个数做算术加法。

深度和宽度可以这样区分：

- **深度：** 后一步依赖前一步提供入口或结果，例如“先找报告，再读报告”。
- **宽度：** 需要处理多个分支，例如“读报告取得 A，读网页取得 B”。

宽度扩展能生成多分支任务，但仍不自动意味着必须组合多段历史经验。后者还需指定哪些历史经历分别支持 A、B，并做单段与组合对照；这属于本课题需要新增的评测设计。

### 4.3 已有答案为什么还要记录轨迹

只保存“问题—答案”，很难检查 Agent 应该查什么、调用哪些工具，以及哪些观察支持答案。

因此，轨迹还应保留工具、参数、返回内容和中间推理。对于深度扩展，构建器可以保留“目录给出报告链接”“报告给出项目数”两部分及其依赖，不必等复杂题生成后才从零寻找全部依据。

论文说明简单题可直接执行并记录，复杂题可在逐步扩展与验证中保留过程；正式版还使用 Oagents 采样训练轨迹。需要区分：**构建时拼接保留的参考过程**，与**独立 Agent 只看最终题面后完整执行得到的轨迹**，二者不能默认相同。

## 5. 方法三：检查扩展是否真的成立

### 5.1 为什么只检查新增部分

原子题已经经过筛选。扩展时，作者希望复用已经检查过的部分，把主要审核成本花在新关系与最终题面的拼接上。

在目录—报告例子里，已有部分是“报告能支持 73 项这个答案”；新增部分是“目录中给定的机构与日期能定位到这份报告”。检查新增关系，再检查合并后的题目是否仍然表达同一个问题，通常比让 Agent 每次从头解决越来越长的整题更省成本。

但这是一种增量审核策略，不能把它理解成每道最终任务都已经被独立执行验证。

### 5.2 两种最容易出现的错误

**第一种：伪扩展，题面变长却没有增加有效步骤。**

例如把《青禾研究所 2024 年项目报告》改成“青禾研究所关于 2024 年项目的报告”。读者仍能直接定位同一报告，没有新增需要查询的中间信息。论文要求排除这类仅替换同义名称的扩展，并检查上层入口与原入口的关系是否成立。

**第二种：信息泄漏，题目提前给出了本该查到的内容。**

例如：

> 请找到青禾研究所那份记载“2024 年完成 73 项项目”的报告，并回答完成项目数。

虽然要求找报告，但答案“73”已经写在题里，Agent 可以跳过工具。另一种情况是题面仍保留原报告链接，导致本来新增的目录查找可以被绕过。

因此，检查至少要回答三个问题：

1. 新增子问题真的能找到原入口吗？
2. 合并时是否正确替换了原本直接提供的入口？
3. 最终题面是否泄漏答案或保留了跳过新步骤的捷径？

扩展检查主要依赖 LLM 的关系和语言判断，效率较高，但不是形式化证明，也不保证能排除所有捷径。若用于正式 Benchmark，仍建议增加独立端到端求解和抽检。[论文依据：arXiv v2 §3.3、附录 B](https://arxiv.org/html/2506.10055v2)

### 5.3 把整个生成过程串起来

~~~mermaid
flowchart TD
    A[准备网页 PDF 图像等材料] --> B[用工具读取并选取答案]
    B --> C[反向生成原子问题]
    C --> D[比较有工具与无工具的回答]
    D --> E[保留工具侧更有优势的基本题]
    E --> F[深度扩展：增加依赖链]
    E --> G[宽度扩展：合并多个分支]
    F --> H[检查新增关系与题面泄漏]
    G --> H
    H --> I[形成问题 答案 来源与参考过程]
    I --> J[采样轨迹用于训练或开展评测]
~~~

阅读到这里，可以把 TaskCraft 理解为：先做出一批“查一份材料即可回答”的基本题，再通过“先找入口”和“多分支求解”增加复杂度；每次扩展都检查新增关系与信息泄漏。

## 6. 实验怎么验证方法有效

### 6.1 生成效率：优质示例能否帮助生成器更好地出题

这里测的是“出题流程”，不是“做题 Agent”。通过率指生成候选中有多少通过质量检查；耗时指生成或扩展花了多久。提示优化是给生成器放入经过选择的优质例子，让它更容易生成合格任务。

| 生成阶段 | 原通过率 | 优化后通过率 | 原耗时 | 优化后耗时 |
| --- | ---: | ---: | ---: | ---: |
| 原子任务生成 | 54.9% | 68.1% | 29.1 秒 | 23.5 秒 |
| 深度扩展，六次尝试口径 | 41.0% | 51.2% | 31.5 秒 | 30.2 秒 |

该实验支持生成流程可以借助优质样例提高通过率和效率；它评测的是生成器提示优化，不是新任务求解中的经验迁移。[依据：正式版 §4.2、表 2]

### 6.2 下游训练：同规模数据是否优于常规多跳 QA

这里测的是“做题模型”：用生成任务采样得到的解题轨迹训练模型，再到外部 Benchmark 上测试。SFT 是学习示范轨迹，RL 是根据执行结果的奖励继续训练；MHQA 指用来作对照的普通多跳问答训练数据。这样才能检查生成的题目是否有训练价值，而不只是数量多、能通过出题检查。

正式版 §4.3 使用不同底座，在 GAIA、WebWalker、论文表头写作 BrowserComp 的检索基准、HLE 上评估。BrowserComp 对应引用中的 BrowseComp，本笔记保留正式表头标注，避免把它误认为另一项新基准。

Qwen-2.5-7B-Instruct 上，均仅 SFT，正式版表 3 节选如下：

| 训练数据 | GAIA | WebWalker | BrowserComp（原表头） | HLE |
| --- | ---: | ---: | ---: | ---: |
| 7.5k MHQA | 20.4 | 23.4 | 3.6 | 4.2 |
| 7.5k TaskCraft | 36.3 | 55.0 | 12.4 | 16.4 |
| 5k MHQA＋2.5k TaskCraft | 34.0 | 52.6 | 6.4 | 13.2 |

同样数量的训练任务下，TaskCraft 数据带来更高结果，减弱了“只是多给了训练样本”这一解释。任务数相同并不自动等于训练 token 或总计算量完全一致，仍需区分控制口径。[依据：正式版 §4.3、表 3；末句为本笔记分析]

### 6.3 RL 与数据规模扩展

在 Qwen-2.5-32B-Instruct 上，以 5k MHQA＋2.5k TaskCraft 做 SFT 后，GAIA 为 **60.2**，原表 BrowserComp 为 **21.0**；继续使用 8k TaskCraft 任务做 RL 后分别为 **60.8** 和 **24.8**。这是更大训练流程的效果，不是纯粹只替换生成器某个模块的消融。[依据：正式版表 3]

正式版表 5 还固定 Qwen2.5-7B-Instruct 的训练设置，使用不同规模 TaskCraft 数据：

| 训练任务数 | GAIA-103 Pass@3 |
| --- | ---: |
| 1,000 | 17.5% |
| 3,000 | 31.1% |
| 5,000 | 39.8% |

这支持该设置中的训练数据扩展收益。Pass@3 不能与其他表格的单次成功率直接比较，也不能用这条训练曲线反驳 [[EmbodiedCLBench]] 的测试时经验数量曲线：二者改变的变量和学习机制不同。[依据：正式版表 5；比较边界为本笔记分析]

### 6.4 工具上下文消融与证据范围

arXiv v2 表 4 中，去掉输入索引和关系、直接提示 LLM 生成原子题，通过率为 **18.5%**；结构化生成为 **43.0%**，工具调用次数方差从 **1.2** 降至 **0.4**。这支持显式工具上下文有助于生成质量及复杂度稳定性。

原文关于耗时减少的文字与表格算术有不一致：119.7 秒减 86.7 秒为 33.0 秒，因此本笔记不沿用文字中的“28 秒”。该项仅按 arXiv v2 标注，不能与正式版 41k 规模混成同一版本实验。[依据：arXiv v2 §4.5、表 4]

## 7. 对经验迁移与组合 Benchmark 的借鉴

以下是本课题可实施的改造方向，并非 TaskCraft 原文已验证的结论。

### 7.1 从单题扩展改成“历史任务族—新组合任务”

保留原子任务及每次扩展的来源关系，先让 Agent 实际执行基础任务，再生成结构发生变化的新目标：

- **深度轴：** 历史操作相同，新任务增加中间识别与数据依赖；
- **宽度轴：** 不同历史经历提供互补程序，新任务需要多个分支协作；
- **条件轴：** 相同程序换对象、资源约束或工具环境；
- **干扰轴：** 插入表面相似但操作不适用的历史经历。

### 7.2 显式记录需要组合哪几段历史

每个候选新任务保留依赖图，并将依赖节点映射到历史经验来源。对 A+B 组合，至少运行无经验、A、B、A+B 和无关经验五类条件，必要时加入直接给出关键程序的诊断参考。

生成器知道的参考答案、目标任务完整解法不能进入历史经验。优先使用程序、触发条件和边界作为迁移内容，降低直接搬运同一答案的风险。

### 7.3 防止“题变长”代替“组合能力变强”

增加题面长度、工具次数或分支数量，只说明结构更复杂。要解释组合能力，应同时观察：各段经验是否被正确选出、是否被读取、子任务接口是否匹配，以及移除某段后是否丢失必要支持。最终成功率与这些过程指标需共同报告。
