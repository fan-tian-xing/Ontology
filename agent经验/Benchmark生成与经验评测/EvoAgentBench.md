# 智能体经验迁移评测：EvoAgentBench 论文调研及研究思路

## 1. 论文定位

### 1.1 论文全名、发表信息与阅读版本

- **英文全名：** *EvoAgentBench: Benchmarking Agent Self-Evolution via Ability Transfer*。
- **作者：** Xingze Gao、Chuanrui Hu、Hongda Chen 等。
- **正式发表：** *Findings of the Association for Computational Linguistics: EMNLP 2026*，2026 年 10 月，50387–50402 页。属于会议论文集，不是期刊。
- **预印本：** arXiv:2607.05202，首次提交于 2026 年 7 月 6 日。

## 2. 论文动机：会解新题，不一定代表会利用经验

普通 Agent Benchmark 主要测量一次独立执行能否完成任务；记忆类评测通常关注事实记忆、检索与信息保留。这两类评测都不足以单独说明：过去的执行轨迹是否被转化成了能够在新任务中使用的操作程序。

经验迁移评测还存在一个构建难题：历史任务与新任务太接近，提升可能来自答案记忆；两者太远，失败又可能只是因为历史中根本不存在有用经验。因此，作者提出的核心原则是 **ability-supported yet instance-disjoint：能力上有支持，任务实例不重复**。

## 3. 方法一：从实际执行轨迹提炼 Ability

### 3.1 收集不同模型的成功与失败轨迹

作者从网页研究、算法推理、软件工程、知识工作四个领域收集任务，分别基于 BrowseComp-Plus、LiveCodeBench、SWE-Bench Verified、GDPVal。构建阶段使用 Kimi-K2.5、GLM-5.1、DeepSeek-V3.2，保留执行轨迹、输出和验证器结果。

不同模型的轨迹用于对照：哪些操作反复促成成功，哪些行为导致失败，哪些检查能够纠正错误。由此得到的经验不只是单条成功答案的摘要。

### 3.2 Ability 卡片表示什么

每张原始能力卡片包含五类内容：

| 字段 | 含义 | 对经验迁移的作用 |
| --- | --- | --- |
| Trigger | 何时触发 | 判断新任务是否需要该经验 |
| Procedure | 可复用步骤 | 给出实际可执行的方法 |
| Evidence | 对应轨迹片段、输出和验证结果 | 使能力描述有行为依据 |
| Boundary | 适用边界 | 防止把局部经验泛化到不适用场景 |
| Role | Method、Guard 或 Workflow | 区分求解方法、纠错规则和执行控制 |

Method、Guard、Workflow 是标注与诊断维度，并不是三项独立的最终评分指标。[依据：正式版 §3.2.2]

### 3.3 如何避免把“主题相似”当作“经验相同”

原始卡片先用 embedding 相似度召回候选对，再检查它们是否在触发条件、操作过程、成功机制、适用边界等方面等价。三个 LLM 判断器一致同意的候选可自动合并，其余交由领域专家审核。

合并不能只依赖连通性：A 与 B 相容、B 与 C 相容，不自动说明 A、B、C 都是同一能力。作者还检查组内一致性；过于泛化的卡片只保留作标注，不允许它建立迁移关系。[依据：正式版 §3.2.3]

## 4. 方法二：建立 Ability Graph 并约束历史集与测试集

### 4.1 图怎样连接任务

图的节点是任务。两个任务共享至少一种合格的可迁移能力时才连边，边上保留能力标识。某能力至少得到两个不同任务支持、且合并后仍足够具体，才有资格建立边。随后用 Louvain 划分能力社区。

正式版构建过程为：2,605 个源任务 → 从 2,516 个任务提取 7,326 张原始卡片 → 得到 173 个可建立边的规范能力 → 保留 1,128 个可迁移任务节点。最终评测使用其中 795 个任务；另外 333 个图节点不进入该评测划分。[依据：正式版 §3.2.4、§3.3、表 2]

### 4.2 划分的关键保证

每个测试任务必须在同一能力社区内，至少有一个历史训练任务与之共享合格能力；同时，训练集与测试集的源任务实例不重合。无经验模型得分仅作为次要分层信号，避免测试集全是天花板题或地板题。

| 领域 | 数据来源 | 历史训练任务 | 测试任务 |
| --- | --- | ---: | ---: |
| 网页研究 | BrowseComp-Plus | 154 | 65 |
| 算法推理 | LiveCodeBench | 182 | 86 |
| 软件工程 | SWE-Bench Verified | 87 | 56 |
| 知识工作 | GDPVal | 105 | 60 |
| 合计 | 四个领域分别评测 | 528 | 267 |

这一保证是“至少一项能力有历史支持”，不保证测试任务需要的所有能力都已覆盖，也不保证必须组合多段历史才能完成。[依据：正式版 §3.2.5、表 2；后一句为对保证范围的解读]

### 4.3 端到端流程

~~~mermaid
flowchart LR
    A[已有任务与多模型执行] --> B[提炼有证据的能力卡片]
    B --> C[操作等价审核与规范化]
    C --> D[按共享能力连接任务]
    D --> E[划分有历史支持的测试集]
    E --> F[从历史经历形成经验]
    F --> G[在新任务上配对评测]
~~~

## 5. 实验怎么验证基准有用

### 5.1 比较方法与公平条件

实验使用 OpenClaw、Nanobot 两种框架，分别搭配 Qwen3.5-27B、Qwen3.5-397B、Gemma-4-31B，形成六种配置。在每种配置内，任务、工具、时限、评分和基础设置相同，每个任务独立运行三次。

| 条件 | 历史经验怎样进入新任务 |
| --- | --- |
| Vanilla | 无演化状态 |
| Memento | 检索最接近的历史案例 |
| ReasoningBank | 从历史轨迹提炼并检索推理记忆 |
| GEPA | 在训练集演化一个统一提示词，应用于所有测试任务 |
| Anchor Skill | 提供整理后的能力技能，并用策展方能力标签路由 |

Anchor Skill 是诊断参考：技能正文仅来自训练侧证据，但检索使用被测方法拿不到的测试侧能力标签。因此，它能检验“相关技能被正确送达时是否有用”，不能作为可直接部署的自动方法，也不构成所有条件下的严格性能上界。

### 5.2 主实验：经验内容有价值，但自动利用不稳定

正式版表 3 的关键结果：

- Anchor 在 24 个“框架×底座×领域”单元中的提升点估计均为正；六种配置的四领域平均提升，其配对置信区间均不包含零。
- 六种配置等权汇总，Anchor 提升 **7.9 个百分点**，95% 置信区间为 **[5.6, 10.3]**。
- Memento、GEPA、ReasoningBank 分别有 **7、4、6 个单元**出现负向点估计。
- 例如 Nanobot / Qwen3.5-27B / SWE 中，Memento 从 Vanilla 的 **45.8%** 降到 **9.5%**，下降 **36.3 个百分点**。

这些结果支持“历史中存在可迁移程序，但自动经验利用可能失败”。负向点估计不能一律解释成经过显著性检验的退化；同样，Anchor 与自动方法的差距也不能仅归因于检索，因为两者同时存在内容提炼和路由差异。[依据：正式版 §4.2、表 3]

### 5.3 路由消融：固定经验内容，只改变选哪条经验

作者进一步固定技能库及一次注入一条技能的方式，仅改变检索路由。在 OpenClaw × Qwen3.5-397B 上：

| 路由方式 | 算法任务 Hit@1 | 算法任务提升 | 软件工程 Hit@1 | 软件工程提升 |
| --- | ---: | ---: | ---: | ---: |
| 策展方标签 | 不适用 | +11.3 | 不适用 | +10.1 |
| 检索后重排 | 91.9% | +7.8 | 89.3% | +7.3 |
| embedding top-1 | 68.6% | +5.6 | 62.5% | +7.2 |
| 随机 top-1 | 0.0% | +0.0 | 1.8% | +3.7 |

提升单位为百分点。Hit@1 衡量与 Anchor 标签路由所选技能的一致率，不是对所有“有用技能”的完备判定。算法任务上更好的路由伴随更大增益；软件工程中重排虽大幅提高命中率，性能仅比 embedding 多 0.1 点，说明检索命中还不等于执行受益。
## 6. 多维度评估：经验失败发生在哪一步

正式版把经验利用分为 encoding、routing、exposure、uptake：有没有提炼出可用经验、是否选对、是否真正进入工作上下文、是否被执行行为采用。

其中一项补充分析检查了 Trace2Skill：在算法与软件工程的 142 个任务、共 426 次会话中，没有访问辅助参考文件，文件里的程序因而未进入上下文。这提醒我们，技能“已经保存”与“已经被模型读到”是两件事。[依据：正式版 §4.4]

论文还报告相对 Vanilla 的 Agent 轮数变化，并区分全部任务、演化后成功任务和未成功任务。轮数减少可能来自更快失败，不能独立视为效率提升。[依据：正式版 §4.5；解释为本笔记解读]
